Enterprise IT & Cybersecurity Home Lab

A hands-on enterprise-style IT infrastructure and cybersecurity environment built with Oracle VirtualBox on a Windows host.

● Ongoing Lab

Project Overview

I am building an enterprise-style IT infrastructure and cybersecurity home lab using Oracle VirtualBox on a Windows host computer. The purpose of this project is to gain hands-on experience with the technologies and procedures used to deploy, administer, secure, troubleshoot, and document IT infrastructure in a real organization.

The lab currently consists of two virtual machines:

  • ADMIN-01 — Kali Linux: My administration and security workstation.
  • APP-SRV-01 — Ubuntu Server: My application/server machine.

The environment is designed to allow me to practice both IT infrastructure administration and cybersecurity. Rather than only studying these concepts in class, I am configuring the systems myself, testing connectivity, applying security controls, troubleshooting problems, and documenting my work.

The Windows computer acts as the physical host, while Oracle VirtualBox provides the virtualization platform for the Linux systems.

Work Completed

1. Virtual Machine Deployment

I established the initial virtualized environment using Oracle VirtualBox.

The lab contains:

  • A Kali Linux virtual machine
  • An Ubuntu Server virtual machine
  • A Windows host operating system
  • Virtual networking between the Linux systems

Kali Linux serves as the administrative and security workstation, while Ubuntu Server provides the server environment that I will continue building throughout the project.

2. Ubuntu Server Configuration

I deployed Ubuntu Server and configured it as the primary application server.

The server was renamed from the default Ubuntu hostname to: 

APP-SRV-01

The hostname allows the server to follow a naming convention similar to what might be used in an organizational IT environment.

The Ubuntu server uses the account: 

ubuntu

and the terminal prompt identifies the system as: 

ubuntu@app-srv-01

3. Network Configuration

I configured the Ubuntu server with two network interfaces.

Adapter 1 — NAT

The first interface provides external network connectivity through VirtualBox NAT. 


Interface: enp0s3
IP Address: 10.0.2.15
Gateway: 10.0.2.2

Adapter 2 — Host-Only Network

The second interface provides communication between the virtual machines on the isolated lab network. 


Interface: enp0s8
IP Address: 192.168.56.101
Network: 192.168.56.0/24

This gives the lab a separate internal network that can be used for administration, testing, and future security exercises.

4. SSH Remote Administration

I configured OpenSSH on the Ubuntu server so that it can be remotely administered from Kali Linux.

I verified that the SSH service was active and configured the server for remote administration. 


SSH
Port: 22

I also tested connecting from Kali to the Ubuntu server using: 

ssh ubuntu@192.168.56.101

This allows Kali Linux to function as my administrative workstation instead of requiring me to perform every server-management task directly from the Ubuntu console.

5. SSH Key Authentication

I generated and configured an SSH key pair for secure remote authentication.

The Kali workstation contains an SSH private/public key pair, while the Ubuntu server is configured to support public-key authentication.

This provides experience with a more secure method of remote administration than relying solely on passwords.

I also configured SSH so that password-based authentication is disabled after verifying that key-based authentication worked.

The goal is to reduce the risk associated with password-based remote access.

6. Linux User and Privilege Management

I examined the Ubuntu user's permissions and group memberships.

The ubuntu account has membership in groups including: 


sudo
adm
users

The sudo group allows the account to perform administrative tasks when necessary.

This gave me hands-on experience with the Linux principle of privilege management, where administrative capabilities should be controlled rather than automatically granted to every user.

7. UFW Firewall Configuration

I configured the Uncomplicated Firewall (UFW) on the Ubuntu server.

The firewall was configured with: 


Status: active
Logging: on (low)
Default: deny incoming
Default: allow outgoing

SSH was explicitly permitted: 

22/tcp     ALLOW IN

This means unsolicited incoming connections are denied by default, while SSH is allowed so that I can continue administering the server remotely.

The firewall configuration demonstrates the security principle of default deny, where network access is restricted unless it has been explicitly permitted.

8. Firewall Verification

After configuring UFW, I verified the firewall configuration rather than assuming it was working.

The configuration was checked using: 

sudo ufw status verbose

The resulting configuration showed that the firewall was active and that SSH was permitted.

This is an important part of infrastructure administration because security configurations should be tested and verified, not simply configured.

9. Linux System Administration

Throughout the project, I have also practiced basic Linux system administration tasks, including:

  • Navigating the Linux filesystem
  • Using the terminal
  • Managing users and permissions
  • Checking services
  • Working with SSH
  • Managing firewall rules
  • Checking network interfaces
  • Verifying IP addresses
  • Installing and updating packages
  • Troubleshooting configuration problems

I encountered and resolved several issues during the setup process, which reinforced the importance of troubleshooting rather than simply following installation instructions.

10. System Updates and Time Synchronization

I performed system updates on the Ubuntu server and encountered a package-management issue related to system time synchronization.

The system initially reported a problem with repository release-file timestamps. I investigated the issue and corrected the server's time synchronization.

I used: 

chronyc makestep

to correct the system clock and then continued with package management.

This was useful troubleshooting experience because it demonstrated how seemingly unrelated system settings can affect security updates and package repositories.

11. Documentation

I am documenting the lab as I build it rather than waiting until the project is finished.

My documentation includes:

  • Configuration steps
  • Commands used
  • Network settings
  • Security configurations
  • Troubleshooting steps
  • Screenshots
  • Successful test results
  • Explanations of why configurations were implemented

The goal is to create a technical record that demonstrates not only what I configured, but also that I understand why the configuration matters.
